# 시스템 구조 (Unity)

## 대원칙 — 게임 로직을 유니티에서 떼어낸다

가장 중요한 결정 하나.

> **전투·성장·승급·방치 계산은 유니티에 의존하지 않는 순수 C#으로 짠다.**

`MonoBehaviour`, `Transform`, `Time.deltaTime` 을 로직 안에서 쓰지 않는다.

이유:
- 밸런스 검증을 **유니티 없이 콘솔에서 수만 번 돌릴 수 있다** (지금 파이썬으로 하던 일)
- 오프라인 진행 계산을 그대로 재사용할 수 있다
- 테스트가 가능해진다

이 게임은 숫자 밸런스가 전부인 장르라, 이 분리를 안 하면 나중에 반드시 후회한다.

## 3계층

```
┌─────────────────────────────────────────┐
│  Presentation   (Unity)                 │  씬, UI, 애니메이션, 사운드
│    · MonoBehaviour · Addressables       │
├─────────────────────────────────────────┤
│  Simulation     (순수 C#)               │  전투, 성장, 승급, 방치 계산
│    · Unity 참조 0                       │  ← 콘솔에서 단독 실행 가능
├─────────────────────────────────────────┤
│  Data           (순수 C#)               │  캐릭터/층/스킬 정의, 세이브
│    · JSON ↔ POCO                        │
└─────────────────────────────────────────┘
```

어셈블리 정의(`.asmdef`)로 강제한다. `Sim.asmdef` 가 `UnityEngine` 을 참조하지 못하게 막으면
실수로 섞이는 것을 컴파일러가 잡아준다.

```
Assets/
  Scripts/
    Irem.Data/         Irem.Data.asmdef      (Unity 참조 없음)
    Irem.Sim/          Irem.Sim.asmdef       (Unity 참조 없음)
    Irem.Game/         Irem.Game.asmdef      (Unity O)
    Irem.Editor/       Irem.Editor.asmdef    (에디터 전용)
  Data/                *.json  (캐릭터·층·스킬 정의)
  Art/ Scenes/ Prefabs/
Tools/
  BalanceRunner/       .NET 콘솔 — Irem.Sim 을 참조해 밸런스 검증
```

## 핵심 설계 — 절차 생성은 시드만 저장한다

무명 잔상은 수백 명이 된다. 전부 저장하면 세이브가 비대해진다.

> **생성기를 결정론적으로 만들고, 세이브에는 시드만 남긴다.**

```csharp
// 저장되는 것은 이것뿐
struct ShadeRecord {
    long   seed;        // 이 값 하나로 이름·생업·스탯·스킬 전부 복원
    byte   rarity;      // 뽑을 때 확정
    byte   bondi;       // 숨겨진 한계
    byte   currentStar; // 현재 선명도
    byte   awaken;      // 각성 단계
    int[]  inherited;   // 승급으로 물려받은 스킬 (최대 3)
}
```

잔상 1명당 **약 24바이트**. 500명이어도 12KB.

전제: `Shade Generate(long seed)` 가 언제 어디서 호출해도 **같은 결과**를 내야 한다.
`System.Random` 대신 자체 PRNG(xorshift 등)를 쓴다 — .NET 버전에 따라 결과가 달라지면 안 된다.

이 구조는 `05-고유성.md`의 **전승** 기능도 공짜로 해결한다.
다른 플레이어에게 시드 하나만 보내면 그 사람이 똑같은 잔상을 만난다.

## 방치 계산 — 결정론이 핵심

접속을 끊은 8시간 동안 무슨 일이 있었는지 계산해야 한다.

**8시간을 실제로 시뮬레이션하면 안 된다.** 모바일에서 몇 초씩 멈춘다.

| 대상 | 방식 |
|---|---|
| 뜰 생산 (유품·기억 조각) | **폐쇄형 계산.** `생산량 × 경과시간`. 즉시 |
| ~~층 진행~~ | **계산하지 않는다.** 층은 플레이어가 직접 오른다 (`19-방치와-등반.md`) |
| 전투 | 층당 **승패만 판정.** 턴 단위로 돌리지 않는다 |

층 전투를 `06-층-공략.md`대로 **조건 판정 + 전투력 비교**로 설계한 것이 여기서 값을 한다.
확률적 전투가 아니라 결정론적 판정이라 오프라인 계산이 가볍다.

```
방치 상한: 12시간 (그 이상은 쌓이지 않음)
→ 하루 2회 접속 유도. 방치형의 표준 리듬
```

**시간 기준은 서버 시간을 쓴다.** 기기 시간을 쓰면 시계를 돌려 무한 파밍이 된다.
서버가 없는 MVP 단계에서는 로컬로 두되, 나중에 갈아끼울 수 있게 `ITimeProvider` 로 추상화해 둔다.

## 데이터 흐름

```
JSON (사람이 편집)
  ↓ 에디터에서 임포트
ScriptableObject (유니티가 로드)
  ↓ 런타임
POCO (Sim 계층이 사용)
```

JSON을 원본으로 두는 이유: 층 100개와 스킬 수백 개를 유니티 인스펙터에서 손으로 넣는 것은 지옥이다.
텍스트로 편집하고 diff 를 볼 수 있어야 한다.

## 씬은 에디터 스크립트로 조립한다

유니티 씬(`.unity`)은 GUID가 얽힌 YAML이라 손으로 쓰기 어렵다.

> **`Irem.Editor` 에 씬 생성 스크립트를 두고, 메뉴에서 실행해 씬을 만든다.**

```csharp
[MenuItem("이렘/씬 생성/뜰")]
static void BuildGardenScene() { /* 오브젝트·UI를 코드로 배치 */ }
```

- 레이아웃이 코드로 남아 재현 가능하다
- 씬이 깨져도 다시 생성하면 된다
- **코드로 씬을 만들 수 있으니, 내가 전체를 작성해 드릴 수 있다**

세부 조정(위치 미세 수정, 이펙트)은 에디터에서 직접 하시면 된다.

## 유니티 설정 권장값

| 항목 | 권장 | 이유 |
|---|---|---|
| 버전 | **Unity 6 LTS (6000.x)** | 모바일 안정성, 장기 지원 |
| 렌더 | **2D URP** | 2D 방치형에 충분. Built-in보다 배터리 유리 |
| UI | **uGUI (Canvas)** | UI Toolkit은 런타임 모바일에서 아직 까다롭다 |
| 직렬화 | **Newtonsoft Json** (`com.unity.nuget.newtonsoft-json`) | JsonUtility는 딕셔너리·다형성을 못 다룬다 |
| 에셋 | **Addressables** | 캐릭터가 수백 명이라 전부 빌드에 넣으면 앱이 비대해진다 |
| 입력 | Input System | 신규 표준 |
| 스크립팅 | IL2CPP / ARM64 | 구글 플레이 필수 요건 |

DOTween 같은 트윈 라이브러리는 나중에. 초기엔 코루틴으로 충분하다.

## 서버는 언제 필요한가

| 기능 | 서버 필요? |
|---|---|
| 방치 진행, 전투, 승급, 뜰 | ❌ 로컬로 충분 |
| 세이브 백업 / 기기 이전 | ⭕ |
| **전승** (잔상 주고받기) | ⭕ 단, 시드 문자열 교환이라 매우 가볍다 |
| 랭킹 | ⭕ (이 게임에는 권하지 않음) |

**MVP는 완전 로컬로 만든다.** 전승은 시드를 문자열로 만들어
복사·붙여넣기로 주고받게 하면 서버 없이도 시연할 수 있다.

## 구축 순서

각 단계가 끝날 때마다 **실제로 만져볼 수 있는 것**이 나오게 자른다.

| 단계 | 만드는 것 | 확인할 것 |
|---|---|---|
| **0** | 프로젝트 골격, asmdef 3개, JSON 로더 | 캐릭터 8명이 콘솔에 출력된다 |
| **1** | `Irem.Sim` — 생성기 C# 포팅 | 콘솔에서 잔상 100명 생성, 중복 검사 |
| **2** | 전투 판정 + 층 조건 | 24층을 4가지 경로로 클리어 가능한가 |
| **3** | 방치 계산 + 세이브 | 앱을 껐다 켜면 시간만큼 쌓여 있다 |
| **4** | **첫 화면** — 뜰 UI, 잔상 배치 | 손으로 만져지는 게임이 된다 |
| **5** | 소환 + 승급 UI | 뽑고 합치는 핵심 루프 완성 |
| **6** | 층 등반 화면, 스토리 텍스트 | 1막이 플레이 가능 |
| **7** | 도트 스프라이트 교체, 연출 | 보여줄 수 있는 상태 |

**0~3단계는 화면이 없다.** 답답해 보이지만 이 순서가 맞다.
숫자가 재미없으면 그림을 아무리 잘 그려도 재미없고, 3단계까지는 유니티 없이도 검증된다.

4단계에서 처음으로 "이 게임이 재미있는가"를 판단할 수 있다.
거기서 아니면 되돌린다. 그래서 아트를 뒤에 뒀다.
